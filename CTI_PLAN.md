# RADAR CTI upgrade: Phase 0 audit and implementation plan

Date: 2026-11-27. Status: plan only, no code changed yet.

## 1. What exists today (audit)

| Area | Current state |
|---|---|
| Hosting | GitHub Pages, static. Deployed by `.github/workflows/pages.yml` on any push touching `site/**`. No server, no serverless functions. |
| Backend | `radar_pipeline.py` (745 lines, Python stdlib only), runs on a student PC via Windows Task Scheduler ("Radar hourly update" -> `update_site.bat`), then `git push`. |
| Database | SQLite `radar.db`. Tables: `items` (27 columns), `events` (new / score / alert / fetch), `errors`, `meta`. Migrations via `EXTRA_COLS` + `migrate()`, re-validation via `QUALITY_VERSION` (9). |
| Sources | NVD API 2.0 (vulns), CISA KEV JSON (exploitation), 5 RSS feeds: BleepingComputer, Ars Technica, The Verge, TechCrunch AI, The Hacker News. |
| AI | Local Ollama `qwen3:8b`. Arabic summaries checked by `summary_problem()` + `verify()` (evidence list, repetition, truncation, foreign script). Rejected summaries fall back to a data template. |
| Alerts | Telegram bot (token in local env var only). |
| Frontend | Vanilla JS, 4 pages (home, alerts, dashboard, about) + shared `core.js` / `app.css`. Arabic RTL default, English via `?lang=en`. CSP with hashed inline script. Exports `data.json`, `details.json`, `events.json`, `stats.json`. |
| Tests | `test_pipeline.py`, 77 checks passing. |

### Data actually available (counted from radar.db)

- Vulnerabilities: 1,190. Real history is short: almost all were published 2026-11-25 to 2026-11-27 (NVD fetch window). KEV-listed: 19.
- News: 181 since 2026-10-22. By category: security/general 128, AI 36, fixes 8, OS 5, devices 4. **Security news dominates the news pillar (71%).**
- Not stored today: NVD reference tags (`Exploit`, `Patch`, `Vendor Advisory`), CWE weakness type, affected versions (CPE). All are in the NVD response we already download.
- No source of security updates or vendor advisories (third pillar is missing).
- No geographic data anywhere.

## 2. Feasibility per feature

| Feature | Verdict | Why |
|---|---|---|
| Risk scoring | Fully feasible | Computed in the pipeline from CVSS, KEV, NVD reference tags (`Exploit`, `Patch`), age. Needs NVD fields we already download but drop. |
| Trends and analytics | Feasible, limited by history | Vuln history is ~3 days. Options: (a) honest "data starts on X" and history grows daily; (b) one-time NVD backfill of metadata only (score, date, CWE, no summaries) for the last 90 days. KEV has real historical `dateAdded` for every entry, so the KEV trend can be real from day one. |
| Daily report | Fully feasible | Generated by the pipeline once per Riyadh day inside the existing hourly job (no new scheduler). Archive as `site/reports/YYYY-MM-DD.json`. Recommendations come from fixed rules tied to findings (KEV due date, patch tag), never invented by the model. |
| Security updates pillar | Feasible | Add official RSS/JSON sources (for example: Chrome Releases, Mozilla security advisories, Microsoft MSRC, Ubuntu USN, CISA advisories). Each must be tested before use. New item kind `update` with type patch / advisory / release. |
| Threat map | Feasible only partially, data will be sparse | No source gives geography. The only honest path: extract a country from news text only when the article names it explicitly, verify the name appears literally in the text, and store its role (attributed origin / victim location / incident location). Anything else goes to "unlocated". Expect few points. Needs an offline world map (no third-party tile service, CSP stays strict). |
| AI assistant | Needs a decision | GitHub Pages cannot hold secrets or run a model. The model is on the PC. See section 4. |

## 3. Execution order (one phase at a time, verified before the next)

1. **Risk engine**: capture NVD references/CWE/CPE; refresh existing records gradually; `risk_score()` with a documented formula and per-factor explanation; "Unknown" when CVSS and KEV are both missing; badges, sort, filter, chart, detail-page breakdown. Validate the weights against the real distribution before locking them (with the suggested weights a CVSS 9.8 with a public exploit but no KEV tops out at ~65 = Medium; this needs a decision once we see the numbers).
2. **Security updates pillar** (prerequisite for report, trends, assistant): new sources, kind `update`, home tab and filter, and rebalancing so security news does not crowd out general tech news.
3. **Trends**: extend `stats.json` (per-day series per pillar, CWE distribution, KEV over time, period-vs-period comparison); range filters 24h / 7d / 30d / 90d, disabled when there is no data for them; trend sentences computed, not generated.
4. **Daily report**: page `report.html`, archive, timestamps, collection-failure disclosure from `errors`/`events`, PDF via print.
5. **Threat map**: extraction plus validation in the pipeline, offline SVG map, clustering by country, unlocated section.
6. **AI assistant**: per the decision below.
7. **Navigation and UI unification**, then **security / regression testing** and deployment.

Navigation proposal (avoid 8 crowded items): Home (vulns + news + updates tabs), Alerts (risk analysis lives here), Statistics and trends, Daily report, Threat map, About. The assistant is a floating button on every page, not a nav item.

## 4. AI assistant: architecture options

| Option | Cost | Real AI | Works when PC is off | Risk |
|---|---|---|---|---|
| A. Retrieval assistant in the browser over the published JSON, with answers built from real records and sources, plus the Ollama summaries already generated for each item. Clearly labelled "answer built from RADAR data", not a chat model. | 0 | No live model (uses model-written summaries) | Yes | None |
| B. Telegram bot answered by the local Ollama (pipeline already talks to Telegram). | 0 | Yes | No | Low; token stays local |
| C. Serverless proxy (for example Cloudflare Workers) with a free hosted model, key in protected env vars. | 0 within free tier | Yes | Yes | Needs an account the students create; free-tier limits; data leaves the PC |
| D. Expose local Ollama to the internet via a tunnel. | 0 | Yes | No | Not recommended: opens the PC to the internet |

Recommendation: A on the site now (works for everyone, never fabricates), optionally B for live free-form questions.

## 5. Constraints kept

No deletion of features, sources or history; no fake records; no secrets in JS; Arabic RTL default; navy and brass identity; GitHub Pages compatible; no new runtime dependencies (stdlib Python, vanilla JS); cost 0.
